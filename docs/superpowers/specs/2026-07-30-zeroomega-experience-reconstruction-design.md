# SwitchyPeformance 原版体验重建设计

## 目标

SwitchyPeformance 保持自己的 Chrome MV3、React、TypeScript、Rust/WASM 路由内核，
但用户使用它时，应当能按 ZeroOmega 的心智模型完成同一件事。

唯一可见差异限定为：

1. 大规则集下切换和匹配更快。
2. 出错后多出更好的排查和日志入口。

性能实现、日志存储、代理编译等内部实现不应改变原版的日常操作路径。
不复制上游代码、模板、样式或资源；只依据公开可观察的功能和交互重新实现。

## 根因

此前的版本把原版当成了功能列表，而不是交互契约：

- 用“运行状态、代理服务器、自动切换、排查日志”等工具页取代了“配置就是主入口”的模型。
- 每次编辑直接保存，丢失了原版全局草稿、应用、放弃三段式操作。
- 弹窗被做成状态面板，而不是用于一两次点击完成切换和加规则的菜单。
- 高级功能被提升为主导航，导致常用路径、视觉密度和页面层级都偏离原版。

## 体验契约

### 1. 设置页外壳

左侧为固定导航，右侧为单一编辑工作区。

左栏顺序：

1. 设置：界面、通用、导入/导出、主题。
2. 配置：内置配置、所有自定义配置、新建配置。
3. 操作：应用、放弃。

补充能力不应打断这个顺序：排查日志、临时规则、同步、性能参数放入“通用”或对应页面的次级入口，不作为高优先级主流程。

编辑配置后只修改浏览器内存中的草稿。左栏“应用”显示待保存状态；“放弃”还原到上一次已应用配置。路由切换、关闭页面和有未应用编辑时都给出一致的保护提示。

### 2. 配置页

每个配置是一级对象，不再先进入“代理服务器管理”或“规则管理”。点击左栏中的配置后，右侧直接出现其设置。

所有配置页共用页头：颜色、名称、导出、重命名、删除。删除存在引用时，先选择替换目标，再应用替换和删除。

必需配置类型与编辑体验：

| 类型 | 原版式编辑内容 |
| --- | --- |
| 直接连接 / 系统代理 | 内置配置说明与启用状态 |
| 固定代理 | 默认代理、HTTP/HTTPS/FTP 覆盖、HTTP/HTTPS/SOCKS4/SOCKS5、账号密码、绕过列表 |
| 自动切换 | 规则表格、拖动排序、复制、删除、备注、默认目标、规则文本模式、规则列表附加来源 |
| PAC | 在线地址或脚本、刷新、请求头、更新时间和错误 |
| 自动检测 | 检测地址与兜底目标 |
| 规则列表 | 匹配目标、默认目标、格式、来源、文本、刷新 |
| 虚拟配置 | 目标配置选择 |

新建配置采用一个模态框：名称、类型、帮助说明。创建后进入新配置页，但不会自动把它设为当前模式。

### 3. 自动切换规则

自动切换配置内部直接显示规则表，不再单独跳到“自动切换规则”工具页。

规则表必须支持：

- 条件类型、匹配内容、目标配置、排序、删除、复制、备注。
- 基础与高级条件切换。
- 默认目标和“一键重置所有规则目标”。
- 规则文本编辑与校验，退出文本模式前给出明确错误。
- 附加规则列表、远程来源、手动刷新和来源错误状态。

大规则集仍使用虚拟列表或分块渲染，但视觉上保持原版表格语义和操作位置。

### 4. 弹窗

弹窗是菜单，不是仪表盘。默认状态从上到下：

1. 直接连接、系统代理和可选外部代理。
2. 自定义配置，按原版顺序显示。
3. 对自动切换、规则列表等可选默认目标的配置，在同一行显示当前默认目标和下拉箭头。点击行切换模式；点击箭头只修改该配置的默认目标。
4. 当前页面快捷操作：添加永久规则、临时规则下拉菜单。
5. 当前标签页失败请求入口，只在确有可处理失败时显示。
6. 选项入口。

“添加规则”打开原版式的局部表单：条件类型、匹配值、子域层级切换、目标配置、取消、添加。默认使用当前域名建议值。

临时规则以当前域名为入口，展开可用目标配置；选择后立即生效并按设置决定是否刷新页面。

失败请求入口展示失败域名及数量，可选择多项、选择永久或临时目标配置，并可进入详细网络排查页。日志只是此入口的增强，不应替代它。

键盘操作至少恢复：方向键/J/K、0、S、1-9、A、T、O、R、?。

### 5. 快捷入口和导入

- 右键菜单和弹窗中的“当前网站”操作要走同一个规则建议和保存服务。
- `.bak` 导入后，原配置名称、类型、规则、默认目标和代理认证关系必须可见且可编辑。
- 导出采用原版可识别的备份格式，同时保留当前高性能内部数据格式作为可选诊断导出。

### 6. 排查与性能扩展

保留当前的失败请求、路由解释、性能采样和日志导出能力，但放在：

- 弹窗失败请求入口的“详细排查”。
- 通用设置中的“网络请求监控”。
- 自动切换配置页中对应规则/来源的错误提示。

不在普通配置切换前增加同步、数据库、扫描或网络请求。所有大数据处理放在后台、按需运行，并维持 localhost/私网直连规则与可解释日志。

## 实现边界

1. 新建 `original-experience` UI 层，消费现有 `ProfileDocumentV2`、后台消息和 Rust/WASM 编译器。
2. 草稿层独立于已应用配置；页面组件只写草稿，应用时一次性调用现有原子替换接口。
3. 所有弹窗和当前网站规则共用一个 `quick-rule` 模型，保证菜单、失败请求和右键菜单的一致性。
4. 每个模块不超过 2,000 行；通用选择器、模态框、配置图标、草稿操作放到公共模块。
5. 新 UI 不依赖上游源文件、上游 CSS、上游图片或上游编译产物。

## 验收路径

以下路径会被 Chrome 端到端测试覆盖：

1. 新建固定代理配置，填写代理，应用，弹窗可切换。
2. 新建自动切换配置，添加/复制/拖动规则，选择默认目标，应用后路由生效。
3. 在任意网页弹窗中打开“添加规则”，切换匹配层级，加入自动切换。
4. 在任意网页弹窗中添加临时规则，刷新后规则仍只在临时范围内生效。
5. 自动切换配置行的下拉菜单只改默认目标，不意外切换当前模式。
6. 失败请求出现后，可从弹窗选择域名并加入永久或临时规则。
7. 编辑后点击放弃，配置和当前路由回到已应用状态。
8. 删除被引用配置时，替换目标后所有引用正确更新。
9. 导入 `.bak` 后，原本的固定代理、自动切换、PAC、规则列表和虚拟配置均可在左栏打开。
10. 10,000 条与 50,000 条规则下，打开、编辑、应用和普通网页导航不出现主线程长任务。

## 交付顺序

1. 先做设置外壳、草稿/应用/放弃、原版式弹窗菜单。
2. 再做配置类型编辑器和自动切换表格。
3. 最后接入失败请求、临时规则、右键菜单和高级/导入页面。
4. 每段完成都以原版用户路径和性能基准双重验收。
