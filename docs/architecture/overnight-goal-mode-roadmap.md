# SwitchyPeformance 夜间目标模式推进方案

**目标：** 做出一个只支持 Chrome 的独立 MIT 代理扩展。它的使用流程完整覆盖成熟代理切换扩展，同时把自动切换的重计算移出网页加载过程，并提供更能定位问题的日志。

**总任务清单：** `docs/superpowers/plans/2026-07-29-zeroomega-parity-implementation.md`。该文档保留每个文件、测试和提交的细节；本文件只规定夜间连续推进的顺序、停止条件和验收线。

## 已确定的产品边界

- 只做 Chrome 和 Manifest V3。
- 只做浏览器扩展，不安装本地程序、服务、数据库或守护进程。
- 支持 HTTP、HTTPS、SOCKS4、SOCKS5 和 HTTP 账号密码代理。
- 不复制 ZeroOmega、SwitchyOmega 或其他参考项目的代码、素材、文案、翻译或测试；只按用户可见行为重新实现。
- 单个源码文件保持在 2,000 行以内，共用逻辑放进明确的公共模块。

## 当前真实进度

| 区域       | 当前状态                                             | 接下来必须完成的事                                     |
| ---------- | ---------------------------------------------------- | ------------------------------------------------------ |
| 配置数据   | V1/V2 可安全读写，旧配置可迁移，保存失败会回滚       | 完成 V2 编辑器、导入预览和来源状态                     |
| 路由核心   | V1/V2 50,000 条 PAC、WASM 路由解释和有序索引已验收   | 完成真实 Chrome 路由回归                               |
| 自动切换   | V2 已可编译后应用到 Chrome，网页加载时不遍历规则数据 | 补齐规则来源、临时规则和失败事件关联                   |
| 设置页面   | V2 已拆为配置、代理、规则、日志、数据和设置页面      | 补齐各页面的创建、编辑、复制、排序和安全删除           |
| 弹窗操作   | 目前不完整                                           | 补当前网页加规则、失败资源修复、临时规则、右键和快捷键 |
| 日志与恢复 | 已有基础失败记录                                     | 做成有限容量的时间线、路由解释和明确的修复操作         |

## 总体推进顺序

```text
配置安全底座
      |
      v
自动切换编译器 + Chrome 实际生效
      |
      +------------------+
      v                  v
设置页完整管理        弹窗快捷操作
      |                  |
      +--------+---------+
               v
        PAC / 规则列表来源
               v
   日志 / 导入导出 / 同步 / 恢复
               v
      真机性能、代理认证、发布
```

顺序不能倒置。特别是不能先把设置页面做得看似完整，再回头补运行时；那样会再次出现“保存了但 Chrome 没有按预期走代理”的假功能。

## 夜间目标模式规则

每次只拿最靠前、依赖已满足的一个小任务，循环直到这一任务有真实结果：

1. 先写一个会失败的测试，证明要补的行为确实尚未存在。
2. 写最少的实现让测试通过，不顺手重做无关区域。
3. 运行本任务测试、类型检查、完整测试、格式检查；改 Rust 时也运行 Rust 测试和格式检查。
4. 修改 Chrome 代理、扩展权限、WASM 或页面入口时，必须构建扩展，并在真实 Chrome 中验证。
5. 测试通过后独立提交并推送。每一个提交都必须能回退、能构建、能安装。
6. 只有当前关卡通过，才继续下一关；测试红了就停在同一关修，不把错误带到后续功能。

### 不会自动放行的情况

| 情况                                         | 固定处理方式                                             |
| -------------------------------------------- | -------------------------------------------------------- |
| 规则能保存但 Chrome 没有生效                 | 不能进入 UI 工作，先修后台配置应用和真实 Chrome 测试     |
| 自动切换规则顺序被索引改变                   | 立即停止优化，先保证结果与用户规则顺序一致               |
| `localhost`、`127.0.0.1` 或 `::1` 被意外代理 | 作为高优先级回归错误，加入固定绕过测试后才能继续         |
| 失败日志只写 `failed`                        | 不能算排查功能完成，必须记录失败类型、命中规则和建议动作 |
| 浏览器不支持某项 PAC 行为                    | 明确显示 Chrome 限制和降级方式，绝不伪装为已支持         |
| 参考项目文件进入提交                         | 立即取消暂存，保留实现记录但不发布任何参考材料           |

## 今晚优先交付：一条可用的完整主链路

今晚的首要目标不是把所有页面做完，而是交付以下闭环。完成它之后，真实用户才能安全测试性能：

```text
导入或新建配置
  -> 选择自动切换
  -> 新增 “x.com 使用某代理” 规则
  -> 保存时 Rust/WASM 编译一次
  -> Chrome 立即采用生成的代理规则
  -> 打开 x.com 时不扫描整个规则列表
  -> 日志能说出命中了哪条规则、走了哪个代理
```

### 今晚阶段 A：路由主链路

1. 完成 V2 的有序规则计划。简单主机规则可走索引，但不能抢在排在前面的复杂规则之前。
2. 完成 V2 PAC：HTTP、HTTPS、SOCKS4、SOCKS5、按协议代理、直接连接兜底、绕过规则、回环地址保护。
3. 把 V2 编译接进 WASM 和后台，保存配置时编译，网页加载时不再遍历规则数据。
4. 让 Chrome 的 `direct`、`system`、固定代理、PAC、自动检测、自动切换、规则列表和虚拟配置都能正确映射。当前规则列表等待来源编译后映射；不会伪装为可直接运行。
5. 增加路由解释：网址、命中规则、目标配置、代理类型、需要 DNS 的警告和编译耗时。

**阶段 A 新验证记录（2026-07-29）：** V2 检查网址已输出当前配置及虚拟配置的实际落点、命中或待 DNS 判断的规则、目标类型、确定性、警告和索引指标；Rust、TypeScript、格式和生产构建通过。诊断正则使用轻量实现，不支持的 JavaScript 专有语法会明确提示，不会伪造确定结果。WASM 产物约 890 KB，扩展生产包约 2.4 MB。V1/V2 各 50,000 条主机规则的 PAC 编译测试通过，生成源码分别约 3.28 MB 和 1.73 MB；这些是保存时的编译与源码体积结果，不是网页加载耗时。

**阶段 A 放行线：** 10,000 条主机规则能在保存时完成编译；真实 Chrome 打开 `x.com`、`instagram.com`、普通直连网站和本地开发地址都得到预期结果；网页请求过程中没有后台逐条扫描规则的代码路径。

**当前验证记录（2026-07-29）：** 单元、Rust、类型、格式和生产构建均通过；Chrome 自动化通道禁止访问 `chrome-extension://`，因此真实扩展页面回归仍待可访问的 Chrome 验证通道，未标记为完成。

### 今晚阶段 B：用户能完整管理配置

1. 配置页面支持新增、重命名、复制、排序和删除；删除被引用配置时给出替换目标或阻止原因。
2. 固定代理编辑器支持不同协议、账号密码绑定、绕过列表和连接失败时的兜底策略。
3. 自动切换编辑器支持所有条件、启用开关、排序、大规则列表虚拟滚动和明确的“匹配内容”校验。
4. PAC、自动检测、规则列表和虚拟配置都有独立编辑器，不用一个大页面硬塞所有表单。

**阶段 B 放行线：** 用户可以不看开发者工具完成新增代理、建自动切换、导入规则、删除无用配置和恢复配置；861 条、10,000 条规则的页面滚动不会整体卡死。

### 今晚阶段 C：弹窗和快捷修复

1. 弹窗显示所有配置、当前激活配置、Chrome 是否可控制代理和当前页域名。
2. 当前网页可以一键加入直连、固定代理或自动切换；用户可以选择主机通配符、网址通配符等条件。
3. 失败资源列表按页面展示；点击失败资源后能选择加入哪个自动切换配置，而不是写死某个配置。
4. 临时规则有过期时间和标签页范围；右键菜单、快捷键和弹窗操作全部走同一套后台命令。

**阶段 C 放行线：** 用户在 `instagram.com`、`x.com` 或任意失败资源页面不打开设置页，也能正确创建规则并马上复测。

### 过夜后继续的阶段 D：外部规则来源

1. PAC 地址与文件：下载、校验、缓存上次成功版本、失败不覆盖当前有效版本。
2. 规则列表订阅：文本、网址、自定义请求头、手动刷新、定时刷新、来源状态。
3. 导入导出：V2 文件、旧备份 `.bak`、预览、冲突报告、失败回滚。

**阶段 D 放行线：** 网络暂时失败时，用户仍保持上一次能用的规则；导入错误文件不会破坏当前代理配置。

### 过夜后继续的阶段 E：可排查、可恢复、可迁移

1. 日志只保留有限量事件，按标签页、域名和错误类型合并，避免日志本身拖慢网页。
2. 每条失败记录要包含网址、匹配配置、匹配规则、代理结果、Chrome 错误码和下一步操作。
3. 外部代理接管检测、代理控制恢复、扩展服务工作线程重启恢复。
4. Chrome 同步、Gist、WebDAV 同步和冲突处理。

**阶段 E 放行线：** 出现“连不上”时，用户能判断是规则、代理账号、代理服务器、Chrome 接管还是网页自身失败，而不是只看到一列 `failed`。

### 最终阶段 F：真实性能和发布

1. 真实 Chrome 扩展测试：加载、切换、保存、重启、临时规则、失败修复、代理认证和恢复。
2. 规则量测试：100、1,000、10,000、50,000 条；测保存编译时间、PAC 大小、设置页滚动和路由解释耗时。
3. 只把可以复现的数字写进性能报告，不用体感或单次测速下结论。
4. 构建可安装包、检查权限、MIT 文件、净室边界、源码文件大小和公开仓库内容。

**阶段 F 放行线：** 全部自动测试、构建、真实 Chrome 回归和性能基准通过，才标记为“完整功能对齐并完成性能验证”。

## 完成定义

“完成”不等于页面上有按钮，也不等于测试只有单元测试。只有下面四项同时成立，目标才可以关闭：

1. 所有配置类型、规则类型和快捷工作流都能从界面实际使用。
2. 保存后的配置在 Chrome 中真实生效，重启扩展后仍能恢复。
3. 10,000 条自动切换规则不会在网页加载时逐条判断，且本地地址默认不被意外代理。
4. 每个高风险行为都有自动测试或真实 Chrome 验证记录，所有公开提交保持 MIT 净室边界。
